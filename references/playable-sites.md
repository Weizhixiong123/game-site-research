# 在线小游戏与聚合站

## 选建站路线

| 路线 | 适合情况 | 第一版交付 |
|---|---|---|
| 原创单游戏站 | 有一套能玩、有差异的规则，或拥有可用的自有素材 | 首页可直接玩，配操作说明、重开和移动端适配 |
| 授权单游戏站 | 已验证玩家会搜索游戏名，能获得发行方许可 | 合规嵌入，补原创玩法提示、设备说明或常见问题 |
| 开源玩法或自有 Scratch 项目 | 代码及素材允许对应使用，能维护构建 | 可玩页面、许可证与署名、手机和桌面实测 |
| 多游戏盒子 | 有持续、合规的游戏供给，用户要选游戏 | 品牌首页、可浏览的分类、每款游戏独立可玩页 |
| 单游戏入口＋相关游戏 | 已有单游戏流量或可复用模板，也有相关游戏供给 | 保留主游戏首页，加真实有用的同类游戏内页和导航 |
| 网页试玩＋自有 App | 有可维护的移动产品和可测量的安装转化 | 浏览器直接试玩，附清晰 App 入口 |

原创实现先跑通规则、输入、计分、失败和重开。MemoryTest 案例把可玩的 `game.html` 和承接搜索的 `index.html` 拆开，用 GitHub 仓库、静态部署和自定义域名上线。这是一种案例结构，可按现有技术栈改成同页组件或独立游戏页。已有游戏需求可以启发原创设计，具体作品的素材、关卡和代码应以实际许可为准。

第三方路线区分开发者、发行平台和站长。优先使用发行方公开授权的嵌入或 API；后台可用支持多发行方的模板。核对商业用途、广告／分成、署名与分发条件，游戏供给不稳时避免一次铺大量页面。自有或合法授权的 Scratch 项目可打包为浏览器可运行的 HTML。带宽和请求成本显著时再考虑对象存储、Worker 与 CDN 缓存，检查缓存命中、失效策略和文件更新；具体配置和成本以当期文档和实测为准。

## 做可玩页面并扩展

- 用户搜游戏名加 `play online` 时，优先让游戏可启动。单游戏首页保留核心意图，向同类游戏扩展时增加独立页和导航。聚合首页用主题分类、热门和新上架帮用户选游戏。
- 同一个可玩版本的拼写和词序变体合并。不同游戏、独立难度或真正不同的玩法可独立成页，提供各自可玩的内容。外部 iframe 附匹配游戏的说明、操作和相关推荐，不只换标题和嵌入链接。
- 核对手机触控、桌面键盘、加载失败、静音、全屏、重开和广告遮挡。把可玩性做稳后，再按游戏特性考虑每日挑战、分享成绩、难度或排行榜，用实际回访和开玩数据判断价值。
- **经典玩法现代化。** 针对通用玩法做原创实现，保留玩家熟悉的规则，用更清晰的交互、设备支持和模式选择解决旧网页的实际缺口。Solitaired 案例表明老需求也可切入，但先评估成熟竞品和持续投入，与抢发售热点分开判断。
- **每日玩法带回访。** 每日更新一道题，卡关时可分享具体谜题请朋友帮忙，结束后可分享无剧透成绩。先保证更新和出题能力，再评估回访和分享带来的访问。玩家受众相关、规则允许时，可向精选游戏导航自荐已能试玩的游戏。
- 观察开玩率、加载性能、回访、每次访问的页面数、搜索落地页和收入。可用站内广告、发行平台分成、无广告付费或自有 App 导流。历史案例里的千次收入只用于说明不同地区和体验下的差异。
